## 1. Логика расчёта: что проверено

Формулы перенесены из Python без изменений и пересчитаны вручную и автотестами.

| Шаг | Формула | Статус |
|---|---|---|
| Материал | `г × (цена катушки / (вес кг × 1000))` | корректно |
| Электричество | `Вт/1000 × ч × тариф` | корректно |
| Амортизация | `(цена принтера / ресурс ч) × ч` | корректно |
| Работа | моделирование + оператор(всё время печати) + постобработка | корректно |
| База | материал + электричество + амортизация + работа | корректно |
| Сложность | `(материал + электричество) × (k − 1)` | корректно |
| Накладные | `(база + сложность) × коэф` | корректно |
| Итог | база + сложность + накладные + доставка | корректно |

Контрольный пример (K1 · PLA · 100 г · 4 ч печати · 1 ч моделирования ·
30 мин постобработки · доставка 300 ₽) даёт **2 183,36 ₽** — совпадает с расчётом
по исходному Python-коду. С ABS (k = 1.2): **2 226,53 ₽**.

### Замечания к модели (не баги, менять не стал)

| # | Наблюдение | Почему важно |
|---|---|---|
| L1 | **Работа оператора = всё время печати × ставка.** В примере это 800 ₽ из 2 183 ₽ — 37 % себестоимости, больше материала в 6 раз | **Решение владельца (v5.0): оставить как есть** — оператор должен следить за печатью постоянно, чтобы вовремя заметить проблему. В интерфейсе это подписано |
| L2 | Наценка за сложность берётся только с материала и электричества, труд не индексируется | Оправдано: сложность — свойство материала |
| L3 | Доставка прибавляется после накладных, то есть накладные на неё не начисляются | Логично, но помните об этом при больших доставках |
| L4 | Амортизация начисляется и после исчерпания ресурса (остаток уходит в минус) | Теперь появляется предупреждение, но расчёт не блокируется |
| L5 | «Итого» — это **себестоимость**, а не цена продажи. Маржи в модели нет | Для прайса нужна отдельная наценка (есть в простом калькуляторе `print-cost-calculator`) |

## 2. Найденные баги и исправления

| ID | Важность | Проблема | Исправление |
|---|---|---|---|
| B1 | **Высокая** | Повторное нажатие «Сохранить в историю» записывало расчёт второй раз и **дважды списывало ресурс принтера**. В Tkinter-версии кнопка блокировалась, при портировании защита потерялась | Кнопка блокируется после сохранения и показывает «✓ Сохранено»; повторное сохранение того же расчёта отклоняется по сигнатуре входа |
| B2 | **Высокая** | Отрицательные значения принимались: `вес = −5` давал отрицательную стоимость материала и итог **ниже себестоимости** (2 045,36 вместо 2 183,36) | Все числовые поля приводятся к диапазону, поле подсвечивается, появляется предупреждение |
| B3 | Средняя | Деление на ноль обнуляло строку молча: вес катушки 0, ресурс 0, цена 0, мощность 0 | Строка по-прежнему 0, но выводится явное предупреждение с названием принтера/филамента |
| B4 | Средняя | Коэффициент сложности < 1 **уменьшал** стоимость (отрицательная наценка) | Ввод < 1 блокируется при сохранении, в расчёте применяется 1.0 |
| B5 | Средняя | Совпадающие имена принтеров/филаментов перезаписывали данные без подтверждения; «PLA» и «pla» создавали дубли | Поиск без учёта регистра + подтверждение замены |
| B6 | Средняя | Принтер с записями в истории, но нулевым временем печати можно было переименовать → история «повисала» на несуществующем имени | Проверка переименования по наличию любых записей, а не по сумме часов |
| B7 | Низкая | `1e12` граммов и подобное давали `∞` в выводе | Жёсткие верхние границы (100 000 г, 10 000 ч, 100 млн ₽) |
| B8 | Низкая | Введённые вес и время терялись при перезагрузке страницы | Состояние формы сохраняется и восстанавливается |
| B9 | Низкая | Импорт гигантского JSON мог подвесить интерфейс | Лимит 5 МБ, не более 300 принтеров / 300 филаментов / 10 000 записей |
| B10 | Низкая | При переполнении localStorage сохранение падало молча | Явная ошибка, запись в историю всё равно происходит |

## 3. Защита данных и безопасность

| ID | Важность | Проблема | Исправление |
|---|---|---|---|
| S1 | **Высокая** | **Загрязнение прототипа** через импортируемый JSON: ключ `__proto__` в `printers`/`filaments` записывался в обычный объект и менял `Object.prototype` | Ключи проверяются: `__proto__`, `constructor`, `prototype` и NUL отбрасываются, длина ограничена |
| S2 | Средняя | **CSV-инъекция**: имя вида `=HYPERLINK("...")` исполнялось как формула в Excel | Ячейки, начинающиеся с `= + − @`, экранируются префиксом `'` |
| S3 | Средняя | Импорт и сброс уничтожали данные без возможности отката | Автоматическая резервная копия + пункт меню «↩ Восстановить предыдущие данные» |
| S4 | Низкая | Импорт без проверки размера и структуры | Лимит 5 МБ, проверка типа файла, предпросмотр количества записей в диалоге |
| S5 | Низкая | Имена неограниченной длины ломали вёрстку и хранилище | Максимум 60 символов, нормализация пробелов |
| S6 | — | XSS через имена принтеров/филаментов | Проверено: все пользовательские строки проходят `esc()` перед вставкой в HTML; `toast` использует `textContent` |
| S7 | — | Утечка данных | Сетевых запросов нет, всё локально |

## 4. Замечания к исходной Python-версии

Найдено при чтении `TitoV3D Calculator v3.9` (на случай, если десктоп останется в работе):

1. `DEFAULT_DATA.copy()` — **поверхностная** копия: вложенные словари общие с константой.
2. В `delete_history_item` / `delete` используется `item["printer"]` — на старых данных без этого ключа будет `KeyError` (нужен `item.get("printer")`).
3. `calc_cost` обращается к `settings["electricity_price"]` напрямую: если в JSON нет ключа, расчёт падает, хотя `_migrate_data` добавляет только `labor_hour_printing`.
4. Текст в «О программе» говорит, что база включает сложность, а код прибавляет её отдельно — расхождение.
5. Удаление филамента, использованного в истории, не блокируется (в веб-версии добавлена такая же защита, как для принтеров).
